# STD-DOC · 文档写法

> **范围**：开发文档写什么、放哪里、如何区分来源，以及变更后的必要维护。
> **不在本文**：需求、功能规则和架构由各自主题文档负责，见 [CORE-INDEX「信息地图」](../README.md)。
> **查阅**：先读结论与接入要点；信息归属看 §1，写法看 §2，来源看 §3，维护看 §4。

## 0 结论

- 文档采用“一个总纲＋主题文档”两层结构，同一规则只有一个权威位置。
- 先写结论、适用条件和完成标准；命令与权限等外部契约集中写明，内部签名与调用细节以源码为准。
- 用户确认、工程默认和待核实分别标记；设计目标不能证明功能已经实现。
- 改规则时同批修改权威文档、相关引用和小节索引；只做本次改动所需的检查。

### 0.1 接入要点

- **新增内容**：先按 §1 找负责文档；已有归属就写入原处，不另开同主题的“补充版”。
- **改变行为**：先在 [REG-STATE](../registry/REG-STATE-决策与开发状态.md) 说明来源与决定，再更新负责该行为的文档。
- **改标题或路径**：同批检查引用与 `docs/SECTIONS.md`，不保留旧位置的规则副本。
- **描述验证结果**：写明实际检查范围；没有运行证据时使用“规划”“未验证”，不写“已通过”。

## 2 形状与表达

每份权威文档包含文件头、`# 编码 · 标题`、范围块、`## 0 结论`、`### 0.1 接入要点` 和按主题编号的正文；登记类的结论可说明使用方法。

- 文件头使用 `id`、`title`、`parent`、`summary`、`related`、`paths`；除总纲外，`parent` 均为 `CORE-INDEX`。
- `id` 全库唯一，文件名采用 `编码-中文标题.md`；总纲保留 `docs/README.md`。
- `summary` 用一句话说明本文负责的问题；`related` 只列实际存在的文档编码。
- `paths` 只列真实存在、由本文负责的源文件或目录；未来代码路径在正文明确标“规划”。
- 范围块说明负责什么、其他主题去哪查、正文如何定位；接入要点写修改该主题前需要知道的边界。
- 一条只写一个要求，适用条件放句首；默认做法可附一句理由，避免并列多种方案让实现者猜选项。
- 首次引用另一份内部文档时采用相对 Markdown 链接，后续可用文档编码和小节标题；引用直接指向负责文档，不经多层转指。
- 总纲、决策登记和验收文档不复制别处的完整规则或配置表；验收用例可给最小输入和预期结果，并链接依据。
- 内容按职责拆分，不按批次、行数或“新版”拆分；需要新增主题时同批登记进总纲。

命令语法、权限和玩家可见结果是插件的产品契约，保留在文档。类名、方法签名和内部实现步骤在代码存在后以源码为准；实现偏离目标时登记差异，不能把现有行为自动当成新需求。

## 3 来源与生效

| 标记 | 含义 | 写作方式 |
| --- | --- | --- |
| 用户确认 | 用户在本次会话中明确要求或补充的行为 | 登记到 REG-STATE，并指向负责文档；只确认用户实际表达的范围 |
| 工程默认 | 为完成基础版本选择的可调整实现约定 | 标明是默认值，可据此开发；不能写成用户已明确确认 |
| 待核实 | 尚无运行配置、源码或实测支持的环境与既有实现陈述 | 登记核实方法、影响和核实前的处理；不能作为部署成功或验收通过的证据 |

需求约定、代码实现和运行验证分别表示“应当怎样”“实际怎样”和“本次查到什么”。状态只维护在 REG-STATE；规范正文不混入开发进度、交接过程或修订历史。

用户新的明确要求优先于工程默认。资料内部矛盾、资料与用户要求矛盾时，先登记差异并在负责文档统一口径，不把原材料的陈述直接升级为规则。

## 4 最少必要维护

改动完成后，检查本次涉及的文档编码、相对链接、标题引用、来源标记和规则一致性；增删文档或小节时同步更新总纲与 `docs/SECTIONS.md`。

文档改动只做文档检查；代码实现阶段按 ENG-VERIFY 选择相关验证。检查通过且没有新改动、新失败或未解决问题时，不重复运行同一检查。

本项目采用轻量文档维护，不额外建立钩子、观察台、字数门禁、证明报告或专用测试脚手架；确有持续维护需求时再另作决定。
